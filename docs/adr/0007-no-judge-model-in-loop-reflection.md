# 收敛检查不引入判题模型，只做激活式提醒

`loop-reflection` 的已知缺陷是「错位」：固定节奏不知道任务何时已经做对，只能撞一次。自然的改进方向是加一个判题模型，让它判断「当前是否已偏离主线」或「是否在打转」，命中才提醒。

调研后不采用。理由是判题的能力上限和成本都比预期差，而这个插件真正缺的是**触发时机**，不是**判断能力**。

## 证据

**判「一步是否冗余」的上限很低。** RedundancyBench（华为诺亚，[arXiv:2605.29893](https://arxiv.org/html/2605.29893v1)）用反事实定义标注了 200 条轨迹、8000+ 步：删掉某步后任务仍成功，则这步冗余。最好方法 **24.88% step-level F1**，部分方法不如随机猜。人类专家标注一条轨迹约 1 小时，因为必须通看 60+ 步的跨步逻辑——这正是「判题需要全局上下文」的实证。

**判题模型的实际水平被测出来了。** Real-Time Detection and Repair（[arXiv:2608.02464](https://arxiv.org/html/2608.02464v1)）在 161 个标注 prompt 上跑 gemini-2.5-flash 判官：**p_detect 0.548，p_false 0.052**。作者原本假设 0.90/0.02，代入实测后「检测回收率从 82% 掉到 43%，五个种子全部不显著」。

**上下文越长判得越差。** [Classifier Context Rot](https://arxiv.org/pdf/2605.12366)：监控器性能随上下文变长而**下降**。所以「给判官更多上下文」不是线性收益，成本与准确率同向恶化。

**成本不是主要问题，判据的位置才是。** 同一篇 2026-08 的工作用 CUSUM + 单类学习的轻量监控（约 200µs/步）在真实语料上：循环检测 0.48–1.00，目标漂移 0.66–0.86，**且跨部署不重标定即失效**（qwen2.5:7b 标定后直接用到 llama3.1:8b，AUROC 0.527，等同随机）。它和判官失败的类别正好互补：判官在目标漂移上满分、在内容损坏上 0.18；监控反过来。

**判「偏离主线」没有可用的生产实现。** 只有 Apollo/MATS 的 goal drift 评估（[arXiv:2505.02709](https://arxiv.org/html/2505.02709)），建立在合成股票交易环境上——两个互斥目标、动作可量化、能自动算分。它的结论落在**预防侧**（强目标引导显著降低漂移），不是检测侧；并且明确指出模型自陈的目标不可信，必须看行为。

## 本机语料复核

1052 个会话、887 个「连续 ≥3 次相同 `i`」的 run，从 shake artifact 还原真实输出后：

| 类别 | run 数 | 占比 |
| --- | --- | --- |
| 输出每次不同（合理推进） | 575 | 65% |
| 输出完全相同 | 310 | 35% |
| 截断未执行 | 2 | 0.2% |

再收紧到「工具 + 参数 + 输出三者全同」：509 个 run，其中 `advise` 139 个是 `Deferred — primary is mid-turn` 的子系统回执，不是模型打转。`read` 76 个里存在同一文件同一行连续读 16 次、输出一字未变的实例。

结论：**只看 `i` 相同会大面积误判**（65% 是合理推进），必须靠输出相同才成立；而这一层宿主已经做了。

## 宿主已占的层

`packages/ai/src/utils/tool-call-loop-guard.ts`：默认阈值 5，参数规范化时排序键并剔除 `i` 字段，一个回合内的多个调用合成单一哈希，命中后注入 `system-interrupt reason="tool_call_loop_detected"`。配套 `model.loopGuard`（流式推理与散文重复）与 `thinking-loop.ts`。

本机 1052 个会话里，这条 `tool_call_loop_detected` 只出现过 13 次（5 个会话）。即确定性重复既已被覆盖，又几乎不触发——它是长尾，不是主要损耗。

## 为什么激活式提醒仍然成立

Self-Correction Bench（[arXiv:2507.02778](https://arxiv.org/html/2507.02778v2)）：14 个非推理模型上，纠正**外部**错误与纠正**自己**同样错误的差距，平均盲区 **64.5%**。但错误后追加一个 `Wait`，盲区降低 **89.3%**，部分出现负盲区。

作者的机制解释是**激活**，不是提供信息：纠正路径存在但没被触发，一个标记词就能打开。这正是注入 `<loop-reflection turns="N">` 加三个问题在做的事。缺的不是判官，是时机。

## 考虑过的选项

- **不引入（采用）**：插件留在「激活」层，判断权归有全上下文的主模型。代价是「错位」缺陷保留，且「偏离主线」明确不受理。
- **引入但只判局部**：只判「这几步是否在重复」，state 可压到最小。但这一层已被宿主 `ToolCallLoopGuard` 和 gemini-cli 的 `LoopDetectionService` 占据，重复实现只会叠加误报。
- **引入并判全局**：判「是否偏离主线」，需要原始请求 + 全部历史产出。对照 24.88% 与 0.548 两个数字，投入产出比不成立。

## 后果

- 插件的职责边界固定为：**在合适时机投递高质量自检问题**，不判断、不拦截、不评分。
- 两个失败模式从此分开记账：**打转**由宿主确定性守卫覆盖；**偏离主线**不设检测，作为已知空白保留。若将来重开，门槛是「有实测的检测器」，不是「听起来合理的判据」。
- 现有三条自检问题是打转视角，不含「你还在做原来那件事吗」。是否补这一条属于另一个决策，不在本 ADR 范围内。
- 本 ADR 不改变任何代码。配置、注入通道、计数逻辑均不动。
